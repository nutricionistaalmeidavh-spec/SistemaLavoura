# Sistema Lavoura — UI Productization Phase 0–3

## Goal
Transform the current technical JSON-oriented frontend into the first commercial product shell while preserving the existing `presentation.js` contract, P0/P1/P2 behavior, local-first architecture and zero mandatory software cost.

## Scope

### UI-0 — Design system
- Introduce Lavoura semantic design tokens for background, surfaces, accents, text, borders, status colors, radii and elevation.
- Preserve existing legacy theme keys used by the shell contract.
- Prefer off-white/soft-gray page background, white primary surfaces, subtle green secondary surfaces and restrained shadows.
- Use icons instead of decorative photos except where imagery carries real information.

### UI-1 — Shell and navigation
- Replace the current dark top bar + flat navigation with a lighter desktop-admin shell inspired by `frontEnds/shells/desktop-admin` and `library/navigation-kit`.
- Keep the same ten functional screen IDs and existing backend contract.
- Group navigation into Visão geral, Produção, Gestão and Sistema without changing screen IDs.
- Keep responsive behavior for smaller screens.

### UI-2 — Product Runtime
- Introduce a local product runtime layer inspired by `frontEnds/shells/product-runtime`.
- Runtime receives backend description/data and selects specialized components by `screen.kind`.
- Keep a generic fallback for screens not yet productized, so later phases can migrate one screen at a time without backend rewrites.
- Preserve authentication, session validation, load/action semantics and Electron/PWA compatibility.

### UI-3 — Dashboard
- Replace the generic dashboard card grid with a Lavoura-specific overview component.
- Show only real data already exposed by the backend; do not fabricate weather, IoT, satellite imagery or machinery state.
- Primary KPI row: planted area, completed operations, harvest quantity and financial result.
- Main content: crop/operation progress, operational alerts, stock/planning health and concise quick links.
- Avoid excessive cards, photos and equal visual weight across all information.

## FrontEnd references
- `frontEnds/shells/desktop-admin`
- `frontEnds/shells/product-runtime`
- `frontEnds/library/dashboard-kit`
- `frontEnds/library/navigation-kit`
- `frontEnds/library/forms-kit` for future UI-5 compatibility
- `frontEnds/library/dialogs-kit` for future UI-6 compatibility

## Non-goals
- No field map implementation until real geospatial data exists.
- No weather widgets without a real local/optional provider.
- No fake IoT readings.
- No changes to business rules, persistence schema or command semantics.
- No mandatory paid dependency.

## Acceptance criteria
1. Existing P0/P1/P2 functional tests continue to pass.
2. New tests verify semantic tokens, grouped navigation, runtime specialization and dashboard view-model behavior.
3. Web build succeeds.
4. Existing screen IDs/actions remain compatible.
5. Dashboard no longer requires raw JSON interaction for its primary read-only experience.
6. UI remains usable in desktop and narrow viewport layouts.
