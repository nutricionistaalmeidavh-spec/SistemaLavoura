# Sistema Lavoura — Especificação IoT-ready

## Objetivo

Preparar o Sistema Lavoura para aceitar conexões IoT opcionais sem transformar IoT em requisito do produto, sem criar custo recorrente obrigatório e sem exigir que o comprador instale infraestrutura adicional para usar o sistema normalmente.

## Base e isolamento

- Branch de trabalho: `roadmap/iot-ready`.
- Base congelada: `0fd5c1f1a30bed4b0e7c5715f08654479f430ddc` (`migration/standalone-phase-0-8`).
- Esta branch não deve receber merge automático enquanto houver alterações paralelas em andamento na branch de desenvolvimento do produto.
- A implementação deve priorizar arquivos novos em `src/iot/` e testes próprios para reduzir conflitos.
- Alterações em `src/index.js`, `src/presentation.js`, `src/security.js`, UI e migrations existentes ficam para a fase de integração final.

## Restrições de produto

1. O Sistema Lavoura continua sendo vendido por valor único e deve funcionar integralmente sem IoT.
2. O instalador normal do Lavoura não pode exigir Docker, Node-RED, Mosquitto, ChirpStack, Redis, PostgreSQL, broker externo, servidor dedicado, VPS ou SaaS pago.
3. O núcleo deve continuar R$ 0, local-first, self-hosted e operacional offline.
4. Protocolos, gateways, serviços ou softwares externos podem existir apenas como integrações opcionais explicitamente escolhidas pelo cliente quando o hardware utilizado os exigir.
5. A ausência de qualquer adapter IoT nunca pode impedir cadastro de talhões, safras, operações, estoque, financeiro, relatórios, backup ou restore.
6. A primeira etapa de IoT real é somente leitura/telemetria. Escrita e controle físico de equipamentos ficam em fase posterior com proteção adicional.
7. O domínio do Lavoura não pode depender diretamente de marcas, ESP32, ChirpStack, Mosquitto, Node-RED ou outro fornecedor.

## Arquitetura

O núcleo IoT usa contratos neutros:

- `Device`: dispositivo conhecido pelo Lavoura.
- `DeviceCapability`: métricas e comandos que um dispositivo declara suportar.
- `TelemetryReading`: leitura normalizada recebida de qualquer protocolo.
- `DeviceCommand`: intenção de comando, nunca acesso direto ao equipamento.
- `Gateway`: ponto intermediário opcional.
- `FieldDeviceBinding`: vínculo dispositivo ↔ talhão.
- `IoTAdapter`: interface para protocolos ou fornecedores.

Fluxo de leitura:

```text
Hardware -> adapter -> normalização -> persistência SQLite -> EventBus -> alertas/dashboard/relatórios
```

O EventBus representa fatos já persistidos; não é fonte de verdade e não substitui transação de banco.

Fluxo de comando futuro:

```text
Usuário -> RBAC -> validação -> safety guard -> DeviceCommand -> adapter -> equipamento -> ACK -> audit log
```

## Protocolos-alvo

### Primeira linha

- MQTT: integração genérica de gateways e dispositivos que já publiquem telemetria.
- Modbus TCP/RTU: bombas, medidores, controladores, estações e equipamentos industriais/agro.
- LoRaWAN: sensores distribuídos em talhões por meio de gateway/network server do cliente.

### Compatibilidade futura

- HTTP/Webhook.
- OPC UA.
- NB-IoT/LTE-M por adapter de fornecedor/gateway.
- BLE para provisionamento local.

## Dados mínimos

### Device

`id`, `name`, `type`, `protocol`, `manufacturer`, `model`, `gatewayId`, `status`, `lastSeenAt`, `batteryLevel`, `signalStrength`, `metadata`.

### TelemetryReading

`id`, `deviceId`, `metric`, `value`, `unit`, `observedAt`, `receivedAt`, `quality`, `sequence`, `rawPayloadHash`.

### FieldDeviceBinding

`deviceId`, `fieldId`, `installedAt`, `removedAt`, `position`, `notes`.

### DeviceCommand

`id`, `deviceId`, `command`, `payload`, `requestedBy`, `requestedAt`, `expiresAt`, `status`, `acknowledgedAt`, `failureReason`.

## Segurança

Permissões previstas:

- `iot:read`
- `iot:manage`
- `iot:configure`
- `iot:command`

`iot:command` nunca deve ser concedida implicitamente por `iot:manage`.

Toda alteração de configuração, vínculo de dispositivo, comando e mudança de estado operacional deve produzir auditoria.

## Resiliência

- Telemetria duplicada deve ser idempotente quando `deviceId + sequence` ou identificador equivalente estiver disponível.
- Leitura inválida não pode corromper o estado atual do dispositivo.
- Dispositivo offline não pode bloquear inicialização do Lavoura.
- Adapter com falha deve ficar isolado dos demais.
- Reconexão deve usar backoff e nunca loop agressivo.
- Dados históricos não podem ser apagados ao desvincular um dispositivo de um talhão.
- Restore de backup deve preservar tabelas IoT quando presentes.

## Interface

Criar área opcional `Integrações > IoT`, invisível ou claramente inativa quando nenhum dispositivo estiver configurado.

Visões previstas:

- dispositivos;
- gateways;
- telemetria recente;
- saúde/conectividade;
- vínculo com talhões;
- configuração de adapters;
- alertas relacionados a sensores.

A UI de IoT não deve aparecer como requisito de onboarding do produto.

## Estratégia de homologação

A implementação nasce com `MockIoTAdapter`, capaz de simular sensores sem hardware real. Todo o core, persistência, segurança, eventos, dashboard e alertas deve ser testável com esse adapter.

Adapters físicos só são marcados como homologados após testes específicos de reconnect, dados inválidos, duplicidade, desconexão e recuperação.

## Fora de escopo inicial

- compra ou fabricação de hardware;
- controle autônomo de irrigação;
- acionamento de bombas/válvulas em produção;
- suporte universal a qualquer equipamento de mercado;
- cloud obrigatória;
- infraestrutura adicional instalada automaticamente no PC do cliente.
